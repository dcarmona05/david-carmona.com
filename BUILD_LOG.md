## Design system (must be preserved exactly — this took many iterations to land on)
- Font: Space Grotesk (`font-display`), bold sans. NOT a serif — an earlier "editorial serif" direction was fully replaced.
- Background: `#0A0A0A` near-black everywhere.
- Colors: `accent` = `#FF3D81` (magenta, the ONLY color used for anything clickable/interactive — buttons, links, hover states, focus rings), `accent2` = `#D9FF3D` (lime, decorative only), `accent3` = `#3DDBFF` (cyan, decorative only, added later). Never use accent2/accent3 for interactive elements — that was a deliberate rule.
- Favicon: NOT the DC logo — a simple two-overlapping-circles mark (magenta+lime), because the detailed logo turned to noise at 16×16/32×32. `app/icon.svg` (static, two `<circle>`s) is used directly as the browser-tab favicon. `app/apple-icon.js` uses `ImageResponse` from `next/og` to generate a 180×180 PNG dynamically (there's no `apple-icon.png` file — Next.js serves it at the route `/apple-icon`, not a literal `.png` path; confirmed via `next build` + `next start`, `<link rel="apple-touch-icon" href="/apple-icon?...">` shows up correctly in page `<head>`). **Gotcha**: in dev mode, hitting `/apple-icon.png` directly 404s — that's the wrong URL, not a broken feature; the real route has no extension.

## Real bugs hit before (avoid repeating)
- Tailwind's `content` config must include `./lib/**/*.js` or classes referenced only in `lib/work.js` never get generated.
- Injecting generated CSS via `<style>{cssString}</style>` causes a React hydration mismatch (server/client escape quotes differently) — always use `<style dangerouslySetInnerHTML={{ __html: cssString }} />` instead.
- Any auto-scroll `useEffect` (e.g. in a chat widget) must guard on `messages.length === 0` or it fires on mount and jumps the whole page.
- SVG logos: if a `<clipPath>` contains a `<rect>`, that's the clip boundary definition, not a visible background — never strip it thinking it's an opaque bg to remove.

## Deployment status (Netlify)
- **Live and working**: `https://david-carmona.netlify.app` — Home/About/Work/Contact all confirmed 200 via curl. Site created via `netlify-cli init` (project name `david-carmona`, site_id `33c229a5-ac24-4475-957f-e7d040e88fde`), linked to this GitHub repo with CI/CD webhooks (auto-deploys on push to `master`).
- **Gotcha #1 — garbled CLI prompts**: the `netlify init` interactive flow's "build command" / "directory to deploy" prompts got answered out of order due to input timing (sent via `orch-interactive --send`, not a real human typing), saving `cmd="Return"` and `dir="npm run build"` as the dashboard's build settings (i.e. literally broken). Fixed by adding a git-tracked `netlify.toml` (`command = "npm run build"`, `publish = ".next"`) — Netlify docs confirm netlify.toml takes precedence over dashboard build settings, so this didn't require touching the corrupted dashboard values directly.
- **Gotcha #2 — the real deploy blocker**: `package-lock.json` had been generated on David's machine against his **global `~/.npmrc`**, which points at ServiceNow's private internal registry (`https://npm.devsnc.com`, auth token required, VPN/internal-network only). Netlify's build servers can't reach that registry at all, so `npm install` just hung until Netlify's timeout killed it ("Failed during stage 'Install dependencies': Command did not finish within the time limit") — looked like a hang/bug at first, wasn't. **Fixed** by adding a project-level `.npmrc` (`registry=https://registry.npmjs.org/`, this repo only, doesn't touch David's global corporate npm config) and regenerating `package-lock.json` against the public registry. **If package-lock.json ever needs regenerating again, make sure `git diff` shows `registry.npmjs.org` URLs, not `npm.devsnc.com`** — this will silently break any external CI again otherwise (not just Netlify).
- Confirmed `/api/contact` serverless function deploys and runs correctly on Netlify's Next.js runtime — returns the coded graceful 503 ("Contact form is not configured yet") since env vars aren't set yet, not a crash.
- `npm audit` flags high-severity advisories in `next@14.2.35` (the latest 14.2.x patch — no newer 14.x fix exists) that are only resolved by a 15/16 major upgrade. Deliberately not done as part of this deploy (breaking change, out of scope) — actual exposure looks low since this site doesn't use `next/image`, Middleware, or Server Actions, which is what most of the flagged advisories target. Worth a dedicated task later if David wants to address it.
- **Custom domain is live**: `https://david-carmona.com` (with hyphen — see Gotcha #3) and `https://www.david-carmona.com` both confirmed 200 with real site content.
- **Gotcha #3 — wrong domain, twice**: David's actual registered domain (in his Porkbun account, registrant "David Carmona," Carmel-by-the-Sea) is **`david-carmona.com` — WITH a hyphen**. Early in domain setup, I assumed `davidcarmona.com` (no hyphen, based on the `hello@davidcarmona.com` contact email already in `lib/site.js`) without ever confirming the exact string with David. That domain belongs to a completely unrelated person — a Spanish flamenco guitarist also named David Carmona — hosted on Vercel. We spent a long time waiting for nameserver propagation on the *wrong* domain before David caught it by literally visiting the live URL and seeing someone else's site. **If revisiting domain/DNS work, always confirm the exact registered domain string (hyphen, TLD, everything) directly from the registrar account — never infer it from an email address or any other secondary source.**
- **Gotcha #4 — adding a domain in Netlify's UI does NOT create its DNS zone.** After fixing the domain name in Netlify's custom-domain field (`davidcarmona.com` → `david-carmona.com`), the DNS kept returning `SERVFAIL` even though Porkbun's nameservers were already correctly pointed at Netlify (from the earlier, wrong-domain setup — nameservers were literally `dns1-4.p08.nsone.net`, a cluster now orphaned since the zone that used to live there was deleted). Editing the custom domain field alone does not provision a matching Netlify DNS zone. What actually fixed it: clicking through the **"Set up Netlify DNS for www.david-carmona.com"** wizard link (Domain management → click "Pending DNS verification" → scroll to "Use Netlify DNS" box) — that's the step that calls Netlify's `createDnsZone` API under the hood. It returned a **different** nameserver cluster (`dns1-4.p03.nsone.net`, not `p08` — each zone gets its own dedicated cluster), which then had to be re-entered at Porkbun. Also tried calling `createDnsZone` directly via `netlify-cli api` as a shortcut — got a 500 Internal Server Error every time; the dashboard wizard is what actually works. Propagation after entering the *correct* nameservers for the *correct* zone took only a few minutes, versus over an hour of waiting on the wrong domain/zone combo.
